1. 项目概述

1.1 背景与痛点

OneNote 是广泛使用的笔记工具，但对开发人员极不友好：原生没有语法高亮、没有行号、粘贴代码时字体混杂、缩进混乱、无法为代码块命名归档。开发者通常被迫截图代码或使用外部工具粘贴图片，导致代码不可编辑、不可搜索、不可复制。市面上的补齐方案（如 OneMore 的部分功能）或不够专注、或对 SQL / PL·SQL 这类企业开发常用语言支持薄弱。

1.2 产品定位

OneExtend 是一个面向 Windows OneNote 桌面版的原生扩展插件（COM Add-in）。首个功能域为「代码块」——让 OneNote 拥有接近专业 Markdown 编辑器的代码呈现能力；同时在架构上将其设计为多功能域扩展平台，后续可平滑叠加与代码块无关的新功能。

1.3 目标用户

  • 使用 OneNote 记录开发笔记、方案设计、排查手册的软件工程师；
  • Oracle / 数据库方向的 DBA 与后端开发人员（重度 SQL、PL·SQL 用户）；
  • 前端 / 全栈开发人员（HTML、CSS、JavaScript/Node.js、React）；
  • Java 服务端开发人员。

1.4 项目目标

编号目标
G1在 OneNote 中一键插入带语法高亮、等宽字体、可配置行号、自定义名称的代码块，效果所见即所得。
G2插入时可自动美化代码缩进；对 SQL / PL·SQL 提供企业级深度美化与高亮支持。
G3已插入的代码块可重新编辑、重新格式化、复制为纯文本（双向可逆）。
G4架构面向扩展：新功能 = 新模块；新语言 = 新语法包（数据文件，零代码改动）。
G5产品级工程质量：安装卸载干净、崩溃隔离、双语文界面（zh-CN / en-US）。

1.5 非目标（Non-Goals）

  • 不做代码执行、调试、IntelliSense —— 插件只负责「呈现与美化」，不是 IDE。
  • 不支持 OneNote 网页版 / macOS / 移动端 插件本体的运行（插入的代码块本身在所有端正常显示，因为它是原生 OneNote 内容）。
  • 不做 OneNote 同步、笔记本管理类功能（避免与产品自身能力冲突）。
  • 不做联网服务：所有处理本地完成，不上传任何用户数据。
关键结论（先读） 经调研（2026-09）：Microsoft 的 Office.js 网页插件体系至今仅支持 OneNote 网页版，不支持 OneNote 桌面版；OneNote for Windows 10（UWP）已被微软退役，统一到桌面版。因此桌面端唯一成熟的官方扩展机制是 COM Add-in（.NET）+ OneNote Interop API（开源项目 OneMore 已验证该路线可行且活跃维护）。本项目选定该路线，详见第 3 章。

2. 需求分析

2.1 用户故事

编号用户故事
US-01作为后端开发，我在排查 Oracle 问题时想把一段 PL·SQL 存进笔记，希望它关键字有颜色、结构缩进清晰、带行号，以后能直接复制回 PL/SQL Developer 使用。
US-02作为前端开发，我把组件代码贴进 OneNote 后总是格式错乱，希望贴入时自动保持等宽字体与缩进，并标注「OrderCard.tsx」这样的块名称。

US-04作为全栈工程师，我希望插入的代码块日后还能改：双击或右键即可重新编辑源码并更新高亮，而不是变成只能看的"死"内容。

2.4 验收标准（摘要）

  • 在一台全新 Windows 11 + Microsoft 365 OneNote 环境安装后，30 秒内完成首次「插入 PL·SQL 代码块（含行号、标题、美化）」全流程；
  • 插入的块在 OneNote iOS / Android / 网页版打开显示正常（原生内容，无需插件）；
  • 对插入 7 天后的块执行「编辑代码块」，还原源码与原稿逐字符一致（自动化对比测试）；
  • 1000 行 SQL 插入 ≤ 2s，期间 OneNote UI 不冻结（后台线程 + 进度提示）；
  • 新增一门示例语言（如 Go）只需新增一个语法包 JSON 文件，全程无代码改动（扩展性验收演示）。

3.2 语言、框架与运行时决策

决策项决定理由
开发语言C#OneNote Interop（COM）唯一的一等公民生态；OneMore / Gem 等先例均为 .NET；类型安全利于长期维护。
插件宿主运行时.NET Framework 4.8（仅宿主层）OneNote 桌面版 COM 加载器加载经典 .NET Framework 程序集；4.8 内置于 Win10 1809+/Win11，无额外部署。
核心库运行时.NET Standard 2.0渲染核心与 OneNote 零耦合：未来若迁移 .NET 8+ 或复用到 Office.js 网页版（Blazor/TS 移植参考），核心代码原样可用。
UI 框架WPFWindows 桌面原生、高 DPI 完善、样式模板能力强（主题、双语、无障碍）；与 .NET Framework 宿主无缝。
COM 注册Registry（HKCU）+ MSIL AnyCPU 单 DLL免 VSTO Runtime 依赖，安装轻量；x86/x64 通吃。
高亮引擎自研轻量 Tokenizer + 声明式语法包现成库（如 ColorCode）语言覆盖与 Oracle 方言能力不足；自研 = JSON 语法包机制（FR-505）的前提，且可控可测。
格式化引擎每语言 Formatter 插件（SQL/PL·SQL 自研规则引擎，其余括号深度 re-indent）SQL 美化是本产品差异点，值得专门实现；接口统一，第三方可扩展。
安装分发WiX Toolset 生成 MSI，可选代码签名企业可批量部署；卸载干净（NFR-007）。
开源参考OneMore（架构思路参考，独立实现）验证 Interop/Ribbon/页面 XML 可行性；借鉴思想、不复制代码，规避许可证风险。
为什么不用 Office.js（即使未来微软支持桌面版）？ Office.js 的 OneNote API 面向"追加内容"，缺少对既有页面结构的精细读写能力（行号表格、Meta 回读、原位更新），且 UI 被限制在任务窗格。本项目把「渲染核心」放在 .NET Standard 2.0 纯库中，就是为这条迁移路径留好了门：届时只需替换集成层与 UI 层。

4. 总体架构设计

4.1 分层架构

⑦ 宿主层 OneExtend.Addin（net48）COM 入口（IDTExtensibility2）· Ribbon 注入 · 快捷钩子 · OneNote 进程内生命周期
⑥ UI 层（WPF）插入/编辑对话框 · 设置中心 · 命令面板 · 上下文菜单 · 主题与双语资源
⑤ 命令与模块层 OneExtend.Core（netstandard2.0）CommandRegistry · ModuleManifest · 事件总线（EventBus）· 命令面板数据源 —— 扩展性的核心
④ 功能域模块CodeBlock 模块（首期）｜预留：Diagram、Formula、SnippetLibrary…（互不依赖，可独立启停）
③ 渲染引擎（CodeBlock 模块内）Formatter 管线 → Tokenizer → 主题映射 → OneNote XML Builder（纯函数、可单测）
② OneNote 集成层 OneExtend.OneNoteInterop 封装：页面 XML 读写 · 选区定位 · 对象 ID · 结构映射（块 ↔ XML）—— 全项目唯一允许触碰 COM 的位置
① 基础设施 Infrastructure设置仓库（JSON）· 日志 · 本地化 · 语法包加载器 · 版本/更新检查
依赖规则：箭头自上而下单向依赖；③ 渲染引擎与 ⑤⑥⑦ 完全解耦（输入字符串、输出字符串），因此可被任何 UI 复用（预览控件用 WPF 富文本渲染同一份 token 流，保证预览 = 最终效果）。

4.2 模块化与扩展机制（回应"后续扩展无关功能"）

  • 命令注册制：每个功能是一个实现 ICommand 的类，携带元数据（ID、名称、图标、快捷键、Ribbon 分组、是否出现在命令面板）。Ribbon、快捷键、右键菜单、命令面板全部由注册表自动生成 —— 新功能只注册，不改造入口。
  • 模块清单：ModuleManifest 声明模块 ID、版本、依赖、默认启停；设置中心可逐模块启停，禁用模块不加载任何代码。
  • 事件总线：OneNote 侧事件（页面切换、选区变化、页内容更新）通过 EventBus 广播，模块按需订阅，避免轮询与相互调用。
  • 资源扩展：语言 = 语法包 JSON；主题 = 主题 JSON；格式化风格 = 风格 JSON。三者均为数据文件，支持用户导入。
  • 示例推演：未来加「Mermaid 图表渲染」= 新建 Diagram 模块（命令 + 对话框 + 渲染器插件），Core 与既有模块零改动。

5.7 核心交互流程

  1. 用户在 OneNote 中定位光标 → 按 Ctrl+Alt+C（或 Ribbon / 右键）唤起对话框；
  2. 剪贴板有文本则自动填入并启发式识别语言，用户可搜索切换语言（最近使用置顶）；
  3. 编辑器实时高亮，选项区调整行号 / 美化 / 标题，预览区即时刷新（200ms 防抖）；
  4. 点击「插入」（或 Enter）→ 后台线程生成页面 XML → Interop 写入当前页 → 对话框关闭，插入内容在光标处呈现；
  5. 后续：光标置于块内按 Ctrl+Alt+E → 还源码重编辑 → 保存原位刷新。

8. 风险与对策

编号风险对策
R-01OneNote Interop 属弱文档化 API，版本升级可能变动COM 访问全部收敛在 OneNote.OneNote 集成层（单点替换）；启动时探测 OneNote 版本并做兼容矩阵告警；跟踪 OneMore 社区的适配动态。
R-02页面 XML 生成不合 Schema 导致内容损坏XmlBuilder 严格按 OneNote XML Schema 单测；写入前备份页面 XML 到本地（可一键回滚）；发布前覆盖 2016→M365 版本矩阵回归。
R-03超长代码块（数千行）插入慢 / OneNote 卡顿后台线程分块写入 + 进度条；>2000 行弹窗建议拆分；性能红线写入 CI（1000 行 ≤ 2s）。
R-04Ribbon 注入在某些 OneNote 版本不可行M0 首项验证；降级入口（快捷键 + 右键 + 浮动工具条）功能等价，架构三入口同源。
R-05双列行号遇软换行错位FR-204 双模式 + 超长行检测自动建议切换；文档明示取舍。
R-06与 OneMore 等开源项目知识产权边界仅借鉴架构思想，代码全部独立实现；引入任何第三方库前核查许可证；OneMore 为开源项目，参考其公开文档中的行为定义。
R-07杀软 / 企业策略拦截 COM 注册HKCU 注册（免管理员）；提供便携诊断工具输出加载失败原因（日志 + 注册检查）。
